## 1. 背景与目标

### 1.1 现状

write-guard 是单一 `pre_tool_call` 插件（`plugin.yaml` 声明 `provides_hooks: [pre_tool_call]`，唯一入口 `on_pre_tool_call`）。当前仅有一个拦截项：拦截命令/代码/路径中引用系统临时目录（含 Windows 与 POSIX 临时目录路径、临时目录相关环境变量展开等形态），命中返回 `{"action":"block",...}`，未命中放行。

### 1.2 背景（为什么需要扩展）

2026-09-17 实际发生两类未经用户授权的写入：

1. **未经授权覆盖 Hermes 配置**：`D:\myagent\.hermes\config.yaml`（及 `profiles\<任意名>\config.yaml`）被直接覆盖。覆盖前仅等待一次"是否覆盖"询问，未获明确授权即执行。
2. **未经授权写入记忆库**：`hindsight_retain` 被直接调用写入 hindsight 记忆，未获用户任何许可。

现有 write-guard 只拦截临时目录，对上述两类行为无任何防护。用户要求新增两个独立拦截项，从机制上确保这两类写入必须先经用户审批，任何一方（LLM/自动化流程）都无法绕过。

### 1.3 保护资产

- **资产一**：Hermes 主配置（HERMES_HOME 根目录 `config.yaml`）。
- **资产二**：各 profile 配置（`HERMES_HOME\profiles\<任意名>\config.yaml`）。
- **资产三**：HERMES_HOME 下其余 config 命名文件（如 `cli-config.yaml` 等；用户决策扩大范围，见 8.1 Q-05）。
- **资产四**：hindsight 记忆库（经 `hindsight_retain` 写入）。
- **资产五**：内置 memory 记忆库（经内置 memory 写工具写入，如 `context_notes`；用户决策纳入，见 8.1 Q-06）。

### 1.4 目标

- **目标一**：对受保护配置文件的"写入/修改"（仅内容写入/覆盖形态，定义见第 2 节术语）工具调用，一律升级到人类审批门，未经用户批准不得执行；读取（含读方向操作）放行；无法判定读写语义的调用默认放行（用户决策，见 8.1 Q-03）。
- **目标二**：对所有写记忆工具（`hindsight_retain` 及内置 memory 写工具）的每次调用一律升级到人类审批门；查询工具放行（用户决策，见 8.1 Q-06）。
- **目标三**：既有临时目录拦截行为完全不变（零改动、零回归）。
- **目标四**：三个拦截项独立实现、互不干扰，按固定轮询顺序 [C, A, B] 组织在同一个插件内（用户决策，见 8.1 Q-01）；任一守卫内部异常不得旁路其他守卫（FR-14）。

### 1.5 平台机制事实（需求依据，已从 Hermes 源码确认）

- `pre_tool_call` 插件 hook 返回 `{"action":"block","message":...}` → 直接阻止工具调用；返回 `{"action":"approve","message":...,"rule_key":...}` → 升级到人类审批门（`tools/approval.py::request_tool_approval`），与危险命令同一条审批通道（once/session/always/deny 粒度家族、超时 fail-closed 阻止、LLM 无法绕过）。
- `rule_key` 控制放行粒度（缺省回退为工具名）；审批门异常时 fail-closed（block）。
- **插件 hook 回调异常由 Hermes 捕获后整个 hook 返回 None（放行）**——守卫内部异常必须由插件自身以项级 try/except 兜住（见 FR-14），不得依赖平台兜底；否则任一守卫异常即静默旁路全部拦截（fail-open），直接违反"不得干扰既有拦截"的核心约束。
- HERMES_HOME 当前值 = `D:\myagent\.hermes`；**受保护目录来源为运行时 HERMES_HOME 环境变量**（未设置时回退默认值），本文档中的绝对路径仅为当前值示例，禁止作为唯一判定依据写死（见 FR-01，对应 MED-2）。
- hindsight 工具：`hindsight_retain`（写）、`hindsight_recall`（查）、`hindsight_reflect`（查），仅 retain 是写操作；hindsight 存在后台自动 retain 队列（内部 writer 线程），走内部路径不经工具调用，`pre_tool_call` 拦截不到（见 Q-07）。
- 内置 `memory` 工具（如 `context_notes`，写内置记忆库）独立于 hindsight provider，同为 `pre_tool_call` 可见工具（用户决策纳入 B 项，见 8.1 Q-06）。

## 2. 术语

- **拦截项（守卫）**：一个独立的"判定 + 处置"单元。本需求共三个：配置写保护（A）、记忆写保护（B）、临时目录拦截（C）。
- **轮询调度**：每次工具调用，从唯一入口按固定顺序 [C, A, B] 从上往下依次执行各拦截项；第一个命中（返回非空处置结果）的项生效并立即返回；全部未命中则放行。
- **"写入/修改"操作集合（用户决策，对应 MED-3）**：仅指对受保护文件的**内容写入/覆盖**形态，包括：复制类命令写至受保护目标（cp 至目标）、echo/tee/重定向写受保护文件、write_file/patch/编辑类工具、execute_code 中明确写受保护文件的代码形态等。**不包含**删除、重命名、移动受保护文件（路径级操作，用户决策不纳入拦截，见 OOS-09）；读方向操作（如 cp 自受保护文件到别处）属读取，放行。
- **明确写形态与无法判定形态（用户决策）**：terminal 等通用工具调用中，能静态识别为"写方向命令 + 受保护路径"者为明确写形态，必须拦截；无法可靠判定读写语义者**默认放行**（低误拦优先，见 8.1 Q-03）。
- **审批门**：平台人类审批通道（`request_tool_approval`），非本插件实现，本插件只负责把命中调用升级进去。

## 3. 功能需求

### 3.1 拦截项 A：Hermes 配置写保护

| 编号 | 需求 | 可测试性 |
|---|---|---|
| FR-01 | **受保护文件判定**：A 项保护范围 = HERMES_HOME 根目录 `config.yaml` + `profiles\<任意名>\config.yaml` + HERMES_HOME 下所有 config 命名文件（含 `cli-config.yaml` 等；用户决策扩大范围，见 8.1 Q-05）。**受保护目录来源 = 运行时 HERMES_HOME 环境变量**（未设置时回退默认值 `D:\myagent\.hermes`）；本文档中的绝对路径仅为当前值示例，禁止将当前值写死为唯一判定依据，否则目录迁移后保护失效（对应 MED-2）。 | 对范围内各路径构造写调用，断言命中；设置不同 HERMES_HOME 值，断言判定随环境变量变化 |
| FR-02 | **命中动作与最低强制工具覆盖集**：对受保护文件的"写入/修改"（定义见第 2 节术语，仅内容写入/覆盖形态）工具调用必须返回 `{"action":"approve",...}` 升级到人类审批门；审批未通过（拒绝/超时）时工具不得执行。**最低强制工具覆盖集**（设计阶段只细化检测方法，不得收缩范围，对应 MED-4）：① write_file：`path` 指向受保护文件；② patch：`path` 指向受保护文件；③ terminal：写方向命令 + 受保护路径（cp 至受保护目标、echo/tee/重定向写受保护文件等明确写形态；无法判定者默认放行，见 8.1 Q-03）；④ execute_code：代码中明确写受保护文件的形态（如以写模式打开受保护配置文件；用户决策纳入，见 8.1 Q-02）。 | 模拟命中，断言返回 approve（对应 AC-02/AC-03） |
| FR-03 | **读取放行**：对受保护文件的读取类访问一律放行，不得触发审批。读取形态包括明确的只读工具（如 read_file）、明确的只读命令形态（如 grep/cat/type 等），以及读方向操作（如 cp 自受保护文件到别处；用户决策，见 8.1 Q-03）。 | read_file 与 cp 读方向指向受保护文件，断言放行 |
| FR-04 | **路径等价判定**：受保护路径判定必须覆盖 Windows 等价写法，至少包括：① 大小写不敏感；② `/` 与 `\` 分隔符等价；③ 环境变量引用形态（如 `%HERMES_HOME%\config.yaml`、`$HERMES_HOME/config.yaml` 等展开后落入受保护目录的写法）；④ 相对路径与上级目录归一化（如先进入受保护目录再写 `config.yaml`、路径含 `.` / `..` 段时归一化后落入受保护目录的写法）。设计阶段可扩充更多等价形态（如 8.3 短名），但不得因识别不全导致上述形态可绕过（对应 MED-2）。 | 大小写、分隔符、环境变量引用、相对路径/上级目录变体断言命中（对应 AC-03） |
| FR-05 | **范围外路径放行**：不在受保护范围内的路径写入不得被 A 项拦截（如 `D:\myagent\workspace\` 下任意文件、其他任意非保护路径）。 | 非保护路径写入断言放行 |
| FR-06 | **审批消息信息完整**：A 项审批消息必须包含被拦截的目标文件完整路径、拦截原因（配置写保护）、发起工具名，确保用户可据此做出知情决策。 | 断言 message 包含路径、原因与工具名（纳入 test_handler.py 用例，见 AC-01，对应 LOW-9） |

> **A 项已知限制（用户已接受，见 8.1 Q-04，对应 LOW-7）**：审批门提供 once/session/always/deny 整个粒度家族；用户选择非单次粒度（once/session/always）后，该项在对应粒度周期内不再逐次审批。此限制经用户知情接受，设计阶段经 `rule_key` 落地。

### 3.2 拦截项 B：记忆写保护（范围扩大，用户决策）

| 编号 | 需求 | 可测试性 |
|---|---|---|
| FR-07 | **写工具审批**：对所有写记忆工具——`hindsight_retain`，以及内置 memory 写工具（写内置记忆库的 `context_notes` 等）——每次调用必须返回 `{"action":"approve",...}` 升级到人类审批门，与参数内容无关；审批未通过（拒绝/超时）时调用不得执行。B 项范围 = 所有写记忆工具，设计阶段不得收缩（用户决策，见 8.1 Q-06）。 | `hindsight_retain` 与内置 memory 写工具任意参数断言 approve（对应 AC-05） |
| FR-08 | **查询工具放行**：`hindsight_recall`、`hindsight_reflect` 以及内置 memory 查询工具一律放行，不得触发审批。 | 断言放行 |
| FR-09 | **审批消息信息完整**：B 项审批消息必须说明被拦截工具名（如 `hindsight_retain`、`context_notes`）与拦截原因（记忆写保护）。 | 断言 message 包含工具名与原因（纳入 test_handler.py 用例，见 AC-01，对应 LOW-9） |

> **B 项已知限制**：与 A 项相同，受审批门 once/session/always/deny 粒度家族约束（见 8.1 Q-04）；自动 retain（后台内部队列）不在拦截范围（用户知情声明，见 Q-07）。

### 3.3 拦截项 C：既有临时目录拦截（行为保持）

| 编号 | 需求 | 可测试性 |
|---|---|---|
| FR-10 | **行为不变**：C 项拦截行为与现状完全一致——命中系统临时目录引用（临时目录路径及临时目录相关环境变量展开等形态）返回 block，未命中放行；拦截消息文本、命中模式集合、覆盖工具范围均不得改变。 | 现有全部用例继续通过（对应 AC-06） |
| FR-11 | **逻辑不被改动**：C 项的判定逻辑不得被新增拦截项附加、合并或改写（配合 NFR-01、CON-04）。 | 代码走查验证 |

### 3.4 轮询调度

| 编号 | 需求 | 可测试性 |
|---|---|---|
| FR-12 | **轮询机制与固定顺序**：唯一入口按**固定顺序 [C, A, B]** 从上往下执行各拦截项（用户决策，见 8.1 Q-01）；第一个返回非空处置结果的拦截项生效并立即返回（命中即返），不再执行后续拦截项；全部拦截项未命中时返回放行。 | 构造同时命中多拦截项的调用，断言只返回排在前面的项的结果（对应 AC-09） |
| FR-13 | **无命中放行**：未命中任何拦截项的正常工具调用必须放行，不得产生新增误拦。 | 合法调用断言放行 |
| FR-14 | **守卫异常隔离契约**（对应 HIGH-1）：每个拦截项以独立 try/except 包裹（项级捕获）；任一守卫内部抛异常时，记录异常日志后**继续轮询后续守卫**，不得中断轮询或令整个插件失效——保证 C 项不被 A/B 异常旁路（fail-open 不发生），A/B 之间亦互不影响。守卫异常兜底必须在插件层自行实现，不得依赖平台对 hook 异常的捕获兜底（平台行为：hook 异常 → 整个 hook 返回放行，见 1.5）。 | 异常注入：人为令守卫 A/B 抛异常，断言 C 仍按原行为命中、其余项不受影响、插件不整体失效（对应 AC-10） |

## 4. 非功能需求

| 编号 | 需求 | 可验证性 |
|---|---|---|
| NFR-01 | **独立性**：三个拦截项独立实现、互不干扰——各自的判定逻辑、判定数据、消息模板相互隔离；任一拦截项的实现变更或内部异常不得影响其他拦截项的行为与既有逻辑。**守卫级异常隔离（FR-14：项级 try/except + 记日志后继续轮询）为强制项**，不得以任何形式放宽（对应 HIGH-1）。 | 代码走查 + 异常注入测试（AC-10） |
| NFR-02 | **可维护性**：判定规则集中、命名清晰、单一职责；规则来源（用户决策/机制事实）有注释说明；后续可独立维护单项而不牵连其他项。 | 代码走查 |
| NFR-03 | **可测试性**：每个拦截项均有自动化测试覆盖命中/未命中/边界变体（大小写、分隔符、环境变量引用、相对路径形态）；测试为只读、无副作用、可重复运行。 | 测试脚本运行 |
| NFR-04 | **回归**：现有 `test_handler.py` 全部用例（scan 用例 + hook 集成用例）必须继续通过，C 项行为零变化。 | `python test_handler.py` 全绿 |
| NFR-05 | **性能**：拦截判定为纯内存计算，不引入 IO/网络/外部调用，对正常工具调用无可感知延迟。 | 代码走查 |

## 5. 约束（用户明确指定，必须满足）

| 编号 | 约束 |
|---|---|
| CON-01 | **单一插件**：扩展在现有 write-guard 插件内完成，不得新建插件。 |
| CON-02 | **独立函数**：A、B、C 三个拦截项各自以独立函数实现，禁止混在一个函数或一份判定逻辑中。 |
| CON-03 | **轮询调度**：每次工具调用按固定顺序 C → A → B 从上往下轮询各拦截项，命中即返，调度行为符合 FR-12（顺序决策见 8.1 Q-01）。 |
| CON-04 | **不得修改既有拦截逻辑**：C 项现有判定与消息逻辑原样保留，不得附加、合并、改写。 |
| CON-05 | **插件协议不变**：仍只提供 `pre_tool_call` 一个 hook。 |
| CON-06 | **流程约束**：REQUIREMENT / DESIGN / CODE_REVIEW 三个环节必须由独立子智能体分别完成，禁止同一智能体跨环节产出（用户明确要求，对应 LOW-6）。 |
