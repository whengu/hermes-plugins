### 1.4 边界 —— 定义不充分（打回主因之一）

### 1.5 待澄清项 —— 识别了 6 条，但漏掉 4 个需求级歧义（打回主因之二）

## 2. 逐条 Findings

### HIGH-1 — NFR-01 异常隔离无机制与验收保障（会导致新逻辑静默瘫痪既有拦截）
- **位置**：NFR-01、FR-12、1.5 节、AC-08
- **问题**：需求要求"任一拦截项的实现变更或内部异常不得影响其他拦截项的行为"，但 FR-12 的轮询机制描述（顺序执行、命中即返）未规定**守卫内部异常的处置语义**。对照已复核的源码事实：插件 hook 回调异常由 Hermes 捕获后**整个 hook 返回 None（放行）**（tool_executor.py `_pre_tool_block` except → None）。若设计按 design-20260917.md 5.2 节的裸 for 循环实现且不加项级捕获，则 A 或 B 任一守卫抛异常 → 整个 write-guard 失效 → **C 项临时目录保护被静默旁路（fail-open）**，直接违反用户"不得干扰之前的拦截"的核心约束，且任何现有测试都抓不住。安全插件的守卫异常要么 fail-closed（block）要么项级隔离后继续轮询，需求必须二选一并给出可验证标准。
- **建议**：① FR-12 增补异常契约：每个守卫独立 try/except，异常记日志后**继续轮询后续守卫**（保证 C 不被旁路），或按项配置 fail-closed；② NFR-01 明确该机制为强制项；③ AC 增补异常注入用例：人为让守卫 A/B 抛异常，断言 C 仍按原行为 block、其余项互不影响、插件不整体失效；④ 注明与平台"hook 异常不阻塞"事实的关系（插件层必须自行兜住）。

### MED-2 — FR-04 路径等价类枚举不完整，存在可绕过写法
- **位置**：FR-04、FR-01、Q-01~Q-06
- **问题**：FR-04 只强制"大小写不敏感、`/` 与 `\` 等价"两类变体，未覆盖：环境变量引用形态（`echo x > %HERMES_HOME%\config.yaml`、`$HERMES_HOME/config.yaml`）、相对路径形态（`cd D:\myagent\.hermes && echo x > config.yaml`）、`..`/`.` 段、8.3 短名（`D:\MYAGEN~1\.hermes\config.yaml`）。这些写法均可能绕过前缀比对。C 项现状对临时目录已识别环境变量形态（%TEMP%/$TMP），A 项需求层未作同类要求，属可预见的绕过向量。
- **建议**：① FR-04 扩充等价类清单（至少含环境变量引用、相对路径归一、`..` 归一），或将"是否解析 HERMES_HOME 环境变量引用/相对路径"提升为新待澄清项；② 同时明确受保护目录来源：运行时读 `HERMES_HOME` 环境变量还是硬编码 `D:\myagent\.hermes`（当前 1.3 节硬编码，若目录迁移则保护失效）。

### MED-3 — "写入/修改"的操作语义边界未定义（删除/重命名/移动）
- **位置**：FR-02、第 2 节术语、OOS-03
- **问题**：用户原话为"写入**和修改**操作"，"修改"是否包含路径级操作——删除（del/rm）、重命名/移动（mv/ren）受保护 config.yaml——需求未定义。若设计只识别内容写入形态（cp/echo/tee/重定向），`del D:\myagent\.hermes\config.yaml` 可绕过；反之若误判读方向（`cp config.yaml backup` 属读取受保护文件，应放行），会造成误拦。FR-02 的绝对表述掩盖了这一未决策点。
- **建议**：FR-02 或术语节显式定义"写入/修改"的操作集合（内容写入 vs 路径级修改），并新增待澄清项让用户确认删除/重命名/移动是否纳入。

### MED-4 — A 项最低强制工具清单缺失，安全范围全部下放设计
- **位置**：FR-02（"覆盖工具范围如何界定……由设计阶段确定"）、Q-02、OOS-03
- **问题**：对安全需求而言，"哪些工具必须受保护"属 WHAT 层，应留在需求层；全部推给设计存在范围收缩风险（设计可能漏掉 patch 的 path 参数、terminal 的 `sed -i`/`mv` 形态等）。Q-02 只覆盖 execute_code 一点。另：Q-03 用户若选"默认放行"，FR-02"一切写入/修改都必须走审批"的绝对表述即与实现不符，需求需在 Q-03 决策后回填限定措辞——该回填义务未写入文档。
- **建议**：FR-02 改为给出**最低强制覆盖集**（write_file/patch 的 path 参数、terminal 写命令形态、execute_code 代码形态——后者待 Q-02 确认），设计只细化检测方法；并注明 Q-03 决策后需回填 FR-02 表述。

### MED-5 — Q-01~Q-06 遗漏 4 个需求级歧义
- **位置**：第 8 节
- **问题**：
  1. 删除/重命名/移动是否属"修改"（见 MED-3）；
  2. HERMES_HOME 环境变量引用/相对路径等价类（见 MED-2）；
  3. **hindsight 自动 retain 边界**：源码显示 hindsight provider 存在后台 retain 队列（plugins/memory/hindsight/__init__.py 的 `_retain_queue`/writer 线程），自动 retain 走内部队列而非工具调用路径——pre_tool_call 拦截不到。B 项只拦截工具调用，需求未说明自动 retain（若启用）不在保护范围，用户可能误以为"所有 hindsight 写入都被拦"；
  4. **内置 `memory` 工具**（context_notes，写内置记忆库，非 hindsight）未被提及：用户只说"hindsight 的写工具"，但若其真实意图是"记忆写入一律审批"，则 `memory` 工具是缺口；需确认意图边界。
- **建议**：增补 Q-07（自动 retain 覆盖边界与用户知情）、Q-08（`memory` 工具是否纳入）、Q-09（删除/重命名语义）、Q-10（HERMES_HOME 环境变量/相对路径等价类）。

### LOW-6 — 用户"三个环节必须独立用子智能体独立完成"过程约束未入档
- **位置**：文档头（第 1 节/上游依据）
- **问题**：用户补充原话明确要求 REQUIREMENT/DESIGN/CODE_REVIEW 三环节独立子智能体完成，属流程级约束；需求文档未记录。虽主要由编排层执行，但文档作为唯一权威依据应留有痕迹，防止设计/编码阶段流程失守。
- **建议**：文档头或约束区注明该流程约束（或显式声明其由编排层负责、不在本文档范围）。

### LOW-7 — Q-04 粒度讨论只点名 always，未涵盖 once/session
- **位置**：Q-04
- **问题**：审批门粒度家族为 once/session/always/deny（已复核），用户选 once/session 同样意味着"非每次调用都审批"，与 FR-02/07"每次调用一律升级审批门"的意图存在同类张力。Q-04 只问 always。
- **建议**：Q-04 措辞扩展为整个粒度家族，或明确"仅首次/会话内放行是否可接受"。

### LOW-8 — "同时命中多拦截项"验收用例依赖 Q-01 顺序决策，AC 未预留
- **位置**：FR-12 可测试性列、AC-01~08
- **问题**：FR-12 的断言方法"构造同时命中多拦截项的调用，断言只返回排在前面的项的结果"在 Q-01 未关闭前不可构造（顺序未定）；AC 清单无对应用例。
- **建议**：Q-01 关闭后增补该 AC 用例，并在需求中标注其前置依赖。

### LOW-9 — 审批消息内容断言未进入 AC 清单

- **问题**：FR-06/09 要求审批消息含路径/原因/工具名（可测试性列写"断言 message 包含…"），但 AC-01 只笼统说"新增 A/B 用例"，未明确消息内容断言为必测项，存在测试只断言 action 不断言 message 的风险。
- **建议**：AC-01 补充"A/B 审批消息内容断言（路径/原因/工具名）纳入 test_handler.py 用例"。
