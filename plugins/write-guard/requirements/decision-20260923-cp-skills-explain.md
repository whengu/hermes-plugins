# 决策记录 2026-09-23：cp 进 ~/.hermes/skills/ 弹审批 = 维持现状（用户裁决）+ 行为可解释性档案

## 触发
agent 用终端 `cp` 向 `<HOME>/skills/safe-config-modify/` 拷文件被弹审批卡。用户提问，
PM 实测复现+归因后，**用户裁决：维持现状（选项 A），要求「可解释，避免出现不可解释的功能」**。

## 行为矩阵实测（当前部署 handler，round16 态）
写判定存在两条**不对称**通道（均有决策史）：

| 操作形 | 结果 | 生效规则 | 决策出处 |
|---|---|---|---|
| `echo>/tee/sed -i/open('w')` 写 `skills/*.md` 等非配置面 | 放行 | 受保护清单=HOME内+yaml/yml/json∪名含config∪.env∪plugins代码 | 用户 2026-09-21「范围要扩大…skills/logs/cache 不保护」 |
| `cp <任意文件> <HOME>/skills/safe-config-modify`（目标位） | **弹** | **cp 通道目标位在 HOME 内一律弹**（不看清单） | 用户红线「cp 是改配置文件的方法，要弹审批」的落地形态（round2/5，宁拦勿漏） |
| `cp a.md <HOME>/logs`、`<HOME>/cache/x`（目标位） | 同样弹 | 同上（证明与 skill 名/含"config"字样**无关**，宽拦是 HOME 级） | 同 |
| `cp <HOME>/skills/… 作为源` / `cp -r` 拷出 | 放行 | 源位=读（红线） | 用户「复制改名不拦源位」 |
| `mv` 改名（绝对形） | 放行 | OOS-09 改名红线 | 用户红线 |
| `cat/less` 读 | 放行 | 读不拦 | 用户红线 |

**为什么 cp 通道不跟清单收窄**（设计理由，非疏漏）：若豁免某子树（如 skills/），
`cp 恶意文件 → 豁免区` + `mv → 保护面`（mv 属改名红线不拦）两跳即可完成配置写入。
宽拦把该链入口焊死；代价=向 skills 拷文件多一次审批（用户判定：可接受）。

## 登记的文案缺陷（round17 收线批修，行为不变）
现 approve 消息模板：「write-guard 配置写保护：工具「X」将写入**受保护的 Hermes 配置文件**：{path}」。
在「cp 目标位=HOME 内非清单面（如 skills 目录）」场景，该文案**失实**——目标并非配置文件，
实际生效的是 cp 通道宽拦规则。这正是本次「不可解释感」的根源：用户按文案找"配置文件"
找不到对应物。修法（≤5 行，纯文案分支，不改判定行为）：`_config_write_disposition`
的 cp-宽拦路径改用独立模板，明说「cp 向 .hermes 目录内任何位置落位须经批准
（防 cp+mv 两跳写配置；读/改名不受限）」。**复审在途（round16）不碰被审文件，随
round17 批施工。**

## 结论
- 拦截行为：维持，不是 bug，是 cp+mv 两跳防御的入口焊死设计；
- 可解释性：本档案 + 决策史引用；待 round17 文案归正后，审批卡本身即可自解释。
