| ④ 守卫实现区 | `_guard_tmpdir`（C）、`_guard_hermes_config`（A）、`_guard_memory_write`（B）三个独立函数 | CON-02：三个拦截项各自独立函数，禁止混写 |
| ⑤ 调度器与入口区 | `GUARDS` 列表、`on_pre_tool_call`（唯一入口，改造为调度器） | FR-12 / CON-03 |

`plugin.yaml`、`__init__.py`、`deploy.py` 均不变（CON-05、OOS-06）。

### 1.2 GUARDS 轮询调度器

固定顺序 **`[C, A, B]`**（Q-01 用户决策 → FR-12 / CON-03）：C 临时目录拦截在最前、A 配置写保护次之、B 记忆写保护最后。

调度语义（FR-12 / FR-13）：
1. 每次工具调用，唯一入口 `on_pre_tool_call` 按固定顺序依次调用各守卫；
2. **命中即返**：第一个返回非空处置结果（dict）的守卫立即生效并返回，不再执行后续守卫；
3. **全不中放行**：所有守卫返回 None 时，入口返回 None（放行）；
4. **异常隔离**：每个守卫的调用以独立 try/except 包裹（FR-14，详见第 5 节）。

调度器结构（伪代码，实现者可直接照做）：

```python
GUARDS = [
    _guard_tmpdir,          # C：临时目录拦截（原样迁移，顺序最前）
    _guard_hermes_config,   # A：配置写保护
    _guard_memory_write,    # B：记忆写保护
]

def on_pre_tool_call(tool_name: str, args: dict, task_id: str = "", **kwargs):
    """唯一入口：按固定顺序 [C, A, B] 轮询各守卫，命中即返，全部未命中放行。"""
    try:
        for guard in GUARDS:
            try:
                result = guard(tool_name, args, task_id)
            except Exception:
                # FR-14：项级异常隔离——记日志后按未命中处理，继续轮询后续守卫
                logger.exception(
                    "write-guard: 守卫 %s 抛出异常，按未命中处理，继续轮询（task=%s）",
                    guard.__name__, task_id,
                )
                continue
            if result is not None:
                logger.info(
                    "write-guard: 守卫 %s 命中（task=%s），返回 action=%s",
                    guard.__name__, task_id, result.get("action"),
                )
                return result
        return None
    except Exception:
        # DR-15：调度器外层防御性兜底（正常不应发生；见 5.3 语义说明）
        logger.exception("write-guard: 调度器整体异常，按放行处理（防御性兜底）")
        return None
```

### 1.3 守卫函数签名约定

统一签名（DR-03，与现有入口参数保持一致）：

```python
def _guard_xxx(tool_name: str, args: dict, task_id: str = "") -> dict | None
```

- **入参**：`tool_name`（发起工具名，用于 A 项消息与 B 项判定）、`args`（工具参数字典）、`task_id`（任务标识，仅用于日志）。
- **返回约定**：`None` = 未命中（继续轮询）；`dict` = 命中处置结果，结构为 `{"action": "block" | "approve", "message": str, "rule_key": str}`（`rule_key` 仅 approve 需要；C 项 block 维持现状结构不变）。
- **副作用约束**：守卫内禁止任何 IO/网络/外部调用（NFR-05 纯内存计算）；禁止修改 `args`。
- **守卫职责边界**：每个守卫只做自己的判定，不得调用或修改其他守卫的判定数据（NFR-01 独立性）；A/B 的判定数据（常量、编译正则）彼此隔离。

## 3. 守卫 A：Hermes 配置写保护

### 3.1 受保护路径判定算法

#### 3.1.1 HERMES_HOME 运行时来源（FR-01 / DR-05）

- **来源**：运行时环境变量 `HERMES_HOME`；**每次调用实时读取**，不缓存（目录迁移即时生效、测试可控）。
- **回退**：环境变量未设置或为空字符串时，回退默认值 `D:\myagent\.hermes`（需求文档 1.5 节给定当前值；该默认值只作回退依据，非唯一判定依据——判定基准永远先取环境变量，DR-05）。
- 实现：

```python
_DEFAULT_HERMES_HOME = r"D:\myagent\.hermes"   # 回退默认值（需求文档 1.5 节当前值示例）

def _hermes_home() -> str:
    raw = os.environ.get("HERMES_HOME") or _DEFAULT_HERMES_HOME
    norm = _normalize_path(raw)
    return norm if norm is not None else _normalize_path(_DEFAULT_HERMES_HOME)
```

#### 3.1.2 受保护文件集合与文件名匹配规则（FR-01 / Q-05 / OOS-02 / DR-06）

**保护范围 = HERMES_HOME 内所有 config 命名文件**，展开为：

1. HERMES_HOME 根目录 `config.yaml`；
2. `HERMES_HOME\profiles\<任意名>\config.yaml`（profile 名任意、深度不限于一层）；
3. HERMES_HOME 下任意深度的其他 config 命名文件（如 `cli-config.yaml` 等，Q-05 用户决策扩大范围）。

**判定实现：不扫描目录（NFR-05 纯内存约束），采用「路径前缀 + 文件名规则」两步判定**（DR-06，备选方案见 9 节 AL-1）：

```python
_SEP = "/"   # 归一化统一分隔符常量（DR-21）：归一化将路径分隔符统一为正斜杠（3.1.3 步骤 4），
             # 因此所有前缀拼接 / 前缀比对 / 文件名提取一律使用正斜杠。
             # 禁用 os.sep：Windows 下 os.sep 为反斜杠，若写成 home + os.sep 会拼出混合分隔符前缀
             # （如 d:/myagent/.hermes\），与全正斜杠的 norm_target 前缀比对恒不相等，
             # 导致 A 项前缀判定静默全失效（fail-open 方向，设计评审 MED-1）。

def _is_protected_config(norm_target: str) -> bool:
    """norm_target 已归一化（小写、绝对、分隔符统一为正斜杠）。"""
    home = _hermes_home()
    if norm_target == home:                      # 指向目录本身：非内容写入，不属保护文件
        return False
    if not norm_target.startswith(home + _SEP):  # 不在 HERMES_HOME 内（DR-21：统一正斜杠常量，禁用 os.sep）
        return False
    filename = norm_target.rsplit(_SEP, 1)[-1]   # 文件名提取同样基于统一分隔符（不依赖 os.sep/os.path，杜绝平台差异）
    return "config" in filename                  # 文件名含 config 字样（已小写归一）
```

**前缀判定分隔符约定（MED-1 / DR-21）**：归一化后的路径一律为全正斜杠形态。此后所有前缀拼接、前缀比对、文件名提取、rule_key 路径拼接（§3.3）**只允许使用统一正斜杠常量，禁止使用 os.sep**——Windows 下 `os.sep` 为反斜杠，与归一化正斜杠混用会拼出不可匹配的混合分隔符前缀，使 A 项全部命中判定静默失效（fail-open 方向）。该约定在实现层以常量定义 + 注释 + 代码走查保证（AC-08 / NFR-02）。

**文件名匹配规则**：文件名（含扩展名，已大小写归一）**包含子串 `config`** 即受保护（如 `config.yaml`、`cli-config.yaml`、`hermes-config.json`、`config.backup.yaml` 等）。该规则为需求词面「config 命名文件」（Q-05）的最小忠实展开——需求三个明确例子（根 `config.yaml`、`profiles\<任意名>\config.yaml`、`cli-config.yaml`）全部被覆盖且无遗漏。边界说明：深度不限（HERMES_HOME 下任意子目录）；HERMES_HOME 内非 config 命名文件（如 `skills\`、`memories\`、`plugins\`、`logs\`、`cron\` 目录下的文件）不属 A 项范围（OOS-02）。该匹配宽度的用户确认事项记入第 12 节未决项 ①。

#### 3.1.3 路径规范化与等价类处理（FR-04 / DR-07）

统一归一化函数，所有路径（目标路径与 HERMES_HOME 本身）先经它归一化再比较（review2 第 6 节改进建议 3 的落地）：

```python
def _normalize_path(text: str) -> str | None:
    """路径归一化。任一步无法处理时返回 None，调用方按未命中/无法判定处理（Q-03）。
    步骤：
    1. 环境变量展开：命令解释器风格（%VAR%）与脚本风格（$VAR、${VAR}）由展开函数处理；
       PowerShell 风格（$env:VAR）手工正则替换；未定义变量保留原样（展开后不落入受保护集合 → 放行）。
       展开语义（MED-3 / DR-23，实现要点见下方「环境变量展开语义（DR-23）」一节）：
       变量名提取使用完整词边界正则 `[A-Za-z_][A-Za-z0-9_]*`（${VAR} 花括号内同规则，防止
       `$HERMES_HOME2` 误匹配 `HERMES_HOME` 前缀）；变量查找一律**大小写不敏感**——Windows 下
       os.environ 原生大小写不敏感，POSIX 下用「键小写化比对」辅助函数查找，保证 `$HERMES_home`、
       `%hermes_home%` 等大小写变体同样展开（否则 POSIX 语义下大小写变体不展开即可绕过保护，见 TC-A-44）。
    2. 引号剥离：整体被单/双引号包裹时去除两端引号。
    3. 字符串转义解义（MED-2 / DR-22）：引号包裹的路径字面量按 Python 字符串转义规则解义——
       `\\` → 单个反斜杠；其余转义序列（如 `\t`、`\n`）按其现实语义解义（制表符/换行等）。
       该步针对 execute_code 常见 Windows 转义写法（如 open("D:\\myagent\\.hermes\\config.yaml","w")）
       与 terminal 命令引号内 `\\` 形态（TC-A-43）；原始字符串（r"..."）形态无转义，直接跳过。
       实现可选「逐转义序列正则解义」或「先解义 `\\` 再统一分隔符」，两种方式结果等价。
    4. 分隔符统一与连续分隔符压缩：反斜杠 → 正斜杠（步骤 3 解义剩余的单反斜杠一并转换）；
       连续正斜杠压缩（`//+` → `/`）——避免解义/转换后出现 `d://myagent//.hermes//config.yaml`
       形态导致前缀比对失败（MED-1/MED-2 配套，DR-21/DR-22）。
    5. 相对段归一：处理 . 与 .. 段。
    6. 绝对化：相对路径基于基准目录拼接后归一。基准声明（LOW-1 / DR-27）：
       terminal 场景 = 命令内目录状态（见 3.2.2，cd 链静态跟踪）；write_file / patch /
       execute_code = **进程当前工作目录（终端 cwd）——此为设计假设，实现期必须对照 Hermes
       源码核实 write_file/patch 相对路径的实际解析基准（workspace、会话目录等）并写入代码注释；
       未核实时维持本假设，依赖 Q-03 默认放行兜底**（跟踪项见第 12 节未决项④）。
    7. 大小写归一：Windows 语义小写化。
    """
```

**四类强制等价形态（FR-04，逐类对应实现步骤，不得因识别不全而绕过）**：

| 等价类 | 实现要点 | 示例 |
|---|---|---|
| ① 大小写不敏感 | 步骤 7：归一化后小写化；受保护基准同样小写 | `D:\MYAGENT\.HERMES\CONFIG.YAML` |
| ② 正反斜杠分隔符等价（含转义字面量与连续分隔符） | 步骤 3/4：字符串转义解义（`\\`→`\` 等，MED-2）→ 反斜杠统一为正斜杠 → 连续正斜杠压缩（`//+`→`/`）后比较 | `D:/myagent/.hermes/config.yaml`、`D:\myagent/.hermes\config.yaml`、`D:\\myagent\\.hermes\\config.yaml`（字符串转义字面量形态，MED-2 / TC-A-43） |
| ③ 环境变量引用形态 | 步骤 1：`%HERMES_HOME%`、`$HERMES_HOME`、`${HERMES_HOME}`、`$env:HERMES_HOME`（PowerShell）展开后落入受保护目录即命中；**查找统一大小写不敏感、变量名完整词边界**（MED-3 / DR-23），大小写变体（`%hermes_home%`、`$HERMES_home`）同样展开命中；变量未定义（展开后原样残留）→ 归一化结果不在受保护集合 → 放行 | `%HERMES_HOME%\config.yaml`、`$HERMES_HOME/config.yaml`、`${HERMES_HOME}\config.yaml`、`$env:HERMES_HOME\config.yaml`、`%hermes_home%\config.yaml`、`$HERMES_home/config.yaml`（大小写变体，MED-3 / TC-A-44） |
| ④ 相对路径与上级目录归一化 | 步骤 5/6：含 `.` / `..` 段归一化后落入受保护目录即命中；terminal 场景额外跟踪命令内 `cd` 链（见 3.2.2），支持「先进入受保护目录再写相对名」形态 | `D:\myagent\.hermes\profiles\..\config.yaml`、`D:\myagent\.hermes\.\config.yaml`、`cd D:\myagent\.hermes && echo x > config.yaml` |

**环境变量展开语义（DR-23 / MED-3，展开函数实现要点）**：
- **变量名边界**：展开函数按完整词边界正则 `[A-Za-z_][A-Za-z0-9_]*` 提取变量名（`$VAR`、`${VAR}`、`$env:VAR` 内同规则），防止 `$HERMES_HOME2` 误匹配 `HERMES_HOME` 前缀（负例 TC-A-47）。
- **大小写不敏感**：所有风格（`%VAR%` / `$VAR` / `${VAR}` / `$env:VAR`）统一按**大小写不敏感**查找环境变量——Windows 平台 `os.environ` 原生大小写不敏感；POSIX 平台实现「键小写化比对」辅助函数（遍历键做小写比对后取对应值）。理由：Windows 环境变量大小写不敏感是用户环境的现实语义；若按 POSIX 大小写敏感语义展开，`$HERMES_home` 等大小写变体不展开即可绕过保护（FR-04 ③ 完备性缺口，TC-A-44）。仅需覆盖 HERMES_HOME 时可特化为「变量名小写化后与 `hermes_home` 比对」，但展开函数应保持通用形态（对命名变量同规则、未定义保留原样）。
- **实现出口**：单独实现 `_expand_env(text)`，**不依赖 `os.path.expandvars`**——该函数对 `%VAR%`（Windows 语义，大小写不敏感）与 `$VAR`（POSIX 语义，大小写敏感）的处理不一致（MED-3 背景）；三种语法风格统一走同一「词边界 + 大小写不敏感查找」内核。
- **展开结果**：继续参与后续归一化步骤，不做特殊旁路；展开后若为相对路径或含 `.` / `..` 段，由步骤 5/6 继续归一。

**归一化前后端一致性（MED-1 / DR-21 配套）**：归一化输出为「全正斜杠 + 小写 + 绝对」形态，是全文唯一比较基准——受保护基准（`_hermes_home`）、前缀比对（§3.1.2）、rule_key 路径（§3.3）均基于该形态，禁止引入 os.sep 或平台分隔符。**「先解义、再统一、后压缩」的顺序不可颠倒**：步骤 3（转义解义）必须在步骤 4（分隔符统一）之前，保证 `D:\\myagent\\.hermes\\config.yaml`（转义字面量）与 `D:/myagent/.hermes/config.yaml`（正斜杠）收敛到同一归一化结果。注：连续分隔符压缩对 UNC 形态（`//server/share`）语义有损，但受保护目录位于本地盘（`D:\myagent\.hermes`），UNC 路径不可能落入受保护集合，不存在漏拦窗口；如未来保护范围扩展至 UNC 路径需另行评估。

**等价类扩充取舍**：Windows 8.3 短文件名格式**不纳入本期实现**（FR-04 中「可扩充更多等价形态」属可选上限，非强制下限；理由与处理见第 8 节 LOW-1 与 DR-17）。

### 3.2 「内容写入/覆盖」形态识别

#### 3.2.1 识别工具集边界（FR-02 / Q-03 / OOS-03 / DR-08）

A 项只对**最低强制工具覆盖集**的四个工具做形态识别：`write_file`、`patch`、`terminal`、`execute_code`（FR-02 ①②③④）。**其他工具一律不扫描、直接放行**——无法判定写语义的调用默认放行（Q-03 低误拦优先；间接写、别名、动态构造路径等形态属 OOS-03 明确不做）。识别方法只细化、不收缩最低强制集（MED-4）。

```python
_CONFIG_SCAN_TOOLS = ("write_file", "patch", "terminal", "execute_code")

def _guard_hermes_config(tool_name: str, args: dict, task_id: str = "") -> dict | None:
    if tool_name not in _CONFIG_SCAN_TOOLS:
        return None                      # 其他工具：不扫描，放行
    if tool_name in ("write_file", "patch"):
        return _judge_path_param(args.get("path"), tool_name)
    if tool_name == "terminal":
        return _judge_terminal(args.get("command"), tool_name)
    return _judge_execute_code(args.get("code"), tool_name)   # execute_code
```

**write_file/patch 路径参数防御行为（LOW-3 / DR-26，对应 TC-A-05）**：`_judge_path_param(path, tool_name)` 首行显式防御——`path` 非字符串类型（None / 数字 / 列表等）或为空串 / 仅空白时**直接返回 None（放行）**。理由：无路径文本可判定即无命中标的；若不防御，None 传入归一化函数会抛异常，虽被项级异常隔离（第 5 节）按未命中兜住，但会留下误导性异常日志——显式防御使行为可预期、日志干净（TC-A-05 断言）。

**统一判定骨架（三形态共用）**：候选路径文本 → `_normalize_path` 归一化（terminal 场景带命令内目录状态）→ `_is_protected_config` 判定是否受保护 → 受保护则确认写语义 → 写语义成立则返回 approve，否则返回 None。

**「内容写入/覆盖」不含**（OOS-09 / Q-03，路径级操作一律不拦）：删除（`del`/`rm`/`os.remove`/`unlink`）、重命名与移动（`ren`/`mv`/`os.rename`/`shutil.move`）、目录创建（`mkdir`）。读方向操作放行（FR-03，见 3.2.2 / 3.2.3）。

#### 3.2.2 terminal 写命令形态（FR-02③ / FR-03 / DR-09）

**判定算法**：
1. 快路径：命令文本中不存在任何受保护路径（归一化匹配）→ 放行；
2. 解析命令内目录状态：按 `&&`、`;` 分割为命令段（管道 `|` 两侧环境独立，不跨管道传播 cd）；每段若以 `cd` / `cd /d`（命令解释器风格）或 `pushd` 引导，则更新该段内当前目录（目标为字面量路径或可展开环境变量时静态解析；`cd ..`、相对目标按段内当前目录归一）；**cd 目标无法静态解析（变量、复杂嵌套）→ 该命令的后续相对路径判定不可信 → 按无法判定处理 → 放行（Q-03）**；
3. 对命令中每个受保护路径出现位置，按下列**写语义判定矩阵**判定方向；任一位置判定为「写」→ 命中 approve；全部为「读」或「无法判定」→ 放行。

**写语义判定矩阵（明确写形态清单）**：

| 形态 | 判定规则 | 方向 |
|---|---|---|
| 输出重定向 `>` / `>>` | 受保护路径紧跟重定向符之后（含 `1>`、`2>`、`&>`；`>>` 追加同为写入） | 写 → 拦 |
| `tee` | 受保护路径为 `tee` 的参数（tee 目标写文件） | 写 → 拦 |
| 复制至目标（`cp` / `copy` / `install`） | 受保护路径为命令的**目标参数**（最后一个路径参数）；受保护路径为**源参数**时为读方向 | 目标写 → 拦；源读 → 放行 |
| 原位编辑（`sed -i` / `perl -pi`） | 命令带原位编辑标志且受保护路径为其操作对象参数 | 写 → 拦 |
| `dd` 的 `of=` | 受保护路径形如 `of=<路径>`（输出文件参数） | 写 → 拦 |
| 内嵌脚本写调用 | 命令文本中含写模式文件打开调用指向受保护路径（如 `python -c "open('受保护路径','w')..."`），判定规则同 3.2.3 写模式清单 | 写 → 拦 |
| 只读命令 | 命令词为明确只读（`grep`/`cat`/`type`/`diff`/`head`/`tail`/`less`/`more` 等）且无上述写特征 | 读 → 放行 |
| 输入重定向 `<` | 受保护路径为 `<` 的来源 | 读 → 放行 |
| 其他 | 无上述任何写特征（含路径仅作参数显示、变量拼接等） | 无法判定 → 放行（Q-03） |

**边界声明**：本矩阵覆盖 FR-02 最低强制集要求的所有明确写形态（重定向、tee、复制至目标）并细化扩充（原位编辑、dd、内嵌脚本）；shell 别名、间接写入、动态构造路径等静态不可可靠识别形态不在覆盖内（OOS-03，默认放行）。

**复制至「受保护目录」形态边界（LOW-5 / DR-25，对应 TC-A-46）**：`cp 源文件 <受保护目录>\`（目标为受保护目录本身 + 尾斜杠）、`cp -t` / `install -t` 等「目标参数为目录」的形态——受保护路径按目录本身判定（归一化后 == home → 非受保护文件）→ 本期**不识别、放行**；实际落盘为目录内源文件名（可能含 config 子串）属**已知静态识别边界（OOS-03）**：落盘文件名依赖命令执行语义（源文件名解析、-t 语义、默认行为），静态可靠识别成本高于收益，显式声明放弃该形态（风险表 R12）。**可选增强方案（本期不实现，仅记录）**：目标为受保护目录时按「源文件名落盘」规则再判定文件名是否含 config；该方案需可靠提取源文件名并区分 cp / install / copy 各语义，误判风险与复杂度高，留待后续评估（如用户要求按 AC-03 同等覆盖再另行立项）。

#### 3.2.3 execute_code 代码形态启发式（FR-02④ / Q-02 / DR-10）

**判定算法**：在代码文本中检测「写方向 API 调用且路径参数（或接收对象）归一化后 ∈ 受保护集合」。相对路径基准 = 进程当前工作目录（execute_code 代码内无 cd 语义；该基准为设计假设，DR-27，实现期对照 Hermes 源码核实，见 3.1.3 步骤 6）。

**写方向形态清单（命中即拦）**：

| 形态 | 判定规则 |
|---|---|
| 写模式文件打开 | `open(受保护路径, 模式)` 且模式串显式含 `w` / `a` / `x`（含 `w`、`wb`、`w+`、`a`、`ab`、`a+`、`x`、`xb`、`x+` 等）；`with open(...) as f:` 同判。**追加 `a` 亦为写入** |
| 路径对象写方法 | `Path(受保护路径).write_text(...)` / `.write_bytes(...)` / `.touch()`；`Path(受保护路径).open(写模式)`（写模式规则同上） |
| 复制至目标 | `shutil.copy(源, 受保护路径)` / `copyfile` / `copy2`（受保护路径为**目标**参数；为源时读方向放行） |
| 底层打开写标志 | `os.open(受保护路径, 标志)` 且标志含 `O_WRONLY` / `O_RDWR` / `O_CREAT` / `O_APPEND` / `O_TRUNC`（写标志形态，属设计细化扩充） |
| 代码内工具调用 | 代码中调用写文件工具（如 `hermes_tools.write_file(path=受保护路径)`、`hermes_tools.patch(path=...)`）且 path 指向受保护文件（属设计细化扩充，与 FR-02① 语义一致） |

**放行形态（明确不拦）**：
- 读模式打开：`open(受保护路径, 'r')` / `'rb'` / 省略模式参数（默认读）；`Path(受保护路径).read_text()` / `.read_bytes()`；
- 删除/移动类：`os.remove` / `os.unlink` / `os.rename` / `shutil.move` 等（OOS-09 路径级操作）；
- 路径仅作字符串出现（`print(受保护路径)`、拼接、比较等）；
- 读写混合模式 `r+` / `r+b`：语义为「可读可写」但静态无法确认实际写入 → 按无法判定默认放行（Q-03）。

**识别实现提示**：用正则匹配写模式打开调用（`open` / `Path(...).open` + 模式参数）、`write_text` / `write_bytes` / `touch`、`shutil.copy` 族、`os.open` 标志、工具调用 path 参数；命中调用后提取路径实参（字面量字符串或可静态展开的环境变量引用）归一化判定；路径实参为动态变量（无法静态求值）→ 该调用按无法判定放行（Q-03）。**转义字面量实参处理（MED-2 / DR-22）**：提取出的路径实参若为引号包裹的转义字面量形态（如 `open("D:\\myagent\\.hermes\\config.yaml","w")`），先按 §3.1.3 步骤 3 解义（`\\`→`\`）再归一化，避免 `//` 残留导致前缀比对失败漏拦（TC-A-43）。

#### 3.2.4 无法判定 → 默认放行（Q-03 / DR-11）

统一兜底原则：**任何形态，只要写语义或目标路径无法静态可靠判定，一律放行**（低误拦优先，用户决策）。本设计不引入任何「疑似即拦」的激进规则；漏拦风险作为已知边界声明（第 9 节 R1）。

### 3.3 A 项 approve 返回结构（FR-02 / FR-06 / Q-04 / DR-12 / DR-16）

```python
{
    "action": "approve",
    "message": "write-guard 配置写保护：工具「{tool_name}」将写入受保护的 Hermes 配置文件：{path}。修改 Hermes 配置须经您批准，请确认后继续。",
    "rule_key": "write_guard:config:{norm_target}",
}
```

- **message**：含目标文件完整路径 + 拦截原因（「配置写保护」）+ 发起工具名（`tool_name`），满足 FR-06 / AC-01 消息内容断言。**路径展示规则（DR-16 + DR-24）**：字面形态命中 → 展示**用户输入原文**（非归一化结果，DR-16，保证可读性）；**等价类变体命中**（相对路径 / 环境变量引用 / cd 链 / 转义字面量等）→ **双段展示**「用户输入原文（对应文件：<归一化解析后的绝对路径>）」，保证用户看到实际将被写入的真实绝对路径（FR-06「完整路径」要求，设计评审 LOW-2；断言见 TC-M-08）。文案汉字表述、无临时目录字面量（第 6 节）。
- **rule_key（DR-12，Q-04 粒度落地）**：`write_guard:config:<归一化目标路径>`——**按目标文件细粒度聚合**。语义：同一受保护配置文件（无论经 write_file / patch / terminal / execute_code 中哪种工具写入）共享同一条放行记录；用户选择 always 后仅**该文件**在该粒度周期内放行，其他配置文件仍逐次审批。理由：① 比固定 rule_key 安全——误选 always 只失效单文件，不会令整个配置写保护整体失效；② 需求 Q-04 已知限制「该项在对应粒度周期内不再逐次审批」中「该项」落地为「该目标文件」，属设计自由度内的最小失效面选择；③ 归一化路径小写稳定、全正斜杠（DR-21），持久化记录跨会话可复现。备选方案对比见第 9 节 AL-2。
- 审批门行为（平台机制，1.5 节事实）：approve 升级到人类审批门，与危险命令同通道（once/session/always/deny）；审批拒绝/超时/审批门异常 → fail-closed 阻止工具执行（见 5.3）。

## 4. 守卫 B：记忆写保护

### 4.1 工具名清单（FR-07 / Q-06 / DR-13）

**写工具清单（命中即拦）**——`_MEMORY_WRITE_TOOLS` 精确集合：

```python
_MEMORY_WRITE_TOOLS = {
    "hindsight_retain",          # hindsight 写工具（1.5 节机制事实：唯一写入口）
    "context_notes",             # 内置 memory 写工具（写内置记忆库）
    # 实现期动作：对照 Hermes 工具注册表核实并补齐其余内置 memory 写工具（见 4.4）
}
```

**查询工具（放行）**——`hindsight_recall`、`hindsight_reflect`（FR-08）、内置 memory 查询工具。实现上**不需要查询清单**：判定 = 「工具名 ∈ 写清单 → 命中；否则 → 放行」（默认放行，查询自然放行）。

**判定与参数无关**（FR-07）：只按工具名判定，不分析 args 内容、不审查记忆内容（OOS-05）。

### 4.2 判定逻辑

```python
def _guard_memory_write(tool_name: str, args: dict, task_id: str = "") -> dict | None:
    if tool_name in _MEMORY_WRITE_TOOLS:
        return {
            "action": "approve",
            "message": "write-guard 记忆写保护：工具「{tool_name}」将写入记忆库。未经您的批准不得写入记忆，请确认后继续。",
            "rule_key": f"write_guard:memory:{tool_name}",
        }
    return None
```

- **精确匹配**（DR-13）：`in` 集合判定，不做前缀/包含/模糊匹配——避免工具名近似导致误拦（低误拦优先，Q-03 精神）。
- **B 项不扫描 args**：查询工具即使参数含敏感内容也放行（FR-08）。

### 4.3 B 项 approve 返回结构（FR-07 / FR-09 / Q-04 / DR-14）

- **message**：含被拦截工具名（`tool_name`）+ 拦截原因（「记忆写保护」），满足 FR-09 / AC-01；文案见第 6 节。
- **rule_key（DR-14）**：`write_guard:memory:<tool_name>`——**按工具名聚合**。语义：B 项拦截与参数无关（FR-07），粒度按工具直观且失效面最小（用户对 `hindsight_retain` 选 always 只放行该工具，其他记忆写工具仍逐次审批）。
- 审批门行为同 A 项（fail-closed，见 5.3）。

### 4.4 内置 memory 写工具全集（实现期核对动作）

需求 Q-06 已决策 B 项范围 = **所有写记忆工具**（hindsight_retain + 内置 memory 写工具）。本设计给出清单骨架（`hindsight_retain`、`context_notes` 为需求明确点名）；**实现期必须对照 Hermes 工具注册表/源码核实内置 memory 写工具全集并补齐集合**（不得收缩范围，MED-4 / FR-07）。识别特征（供核对辅助）：工具名语义为「写入记忆/笔记/上下文记录」且为写方向（区别于查询方向）。该核对动作记入第 12 节未决项 ②。

## 5. 守卫异常隔离（FR-14 / NFR-01 / AC-10）

### 5.1 项级 try/except 实现模式（DR-15）

每个守卫的调用在调度器内以**独立 try/except** 包裹（见 1.2 调度器代码）：

- **异常粒度 = 守卫项**：一个守卫抛异常，只影响该项本次调用；
- **异常处理动作 = 按未命中处理 + 继续轮询**：`logger.exception(...)`（记录堆栈，满足「记录异常日志」）→ `continue`（继续执行后续守卫，满足「继续轮询后续守卫」）；
- **不中断轮询、不令插件失效**：循环结构保证异常后其余守卫照常执行，调度器正常返回（None 或后续守卫命中结果）。

**为什么必须插件层自兜（不得依赖平台）**：平台行为为「插件 hook 回调异常 → 整个 hook 返回 None（放行）」（需求 1.5 节已确认）。若不加项级 try/except，A 或 B 任一守卫抛异常将导致**整个 write-guard 静默失效**（含 C 项）——即 fail-open，直接违反 FR-14 / NFR-01。项级隔离是强制项，不得以任何形式放宽（NFR-01）。

### 5.2 日志与继续轮询

- 日志级别：`logger.exception`（含完整堆栈），日志前缀固定 `write-guard: 守卫 <名> 抛出异常`，便于检索；
- 守卫命中日志：`logger.info`（action + 守卫名 + task_id），便于审计拦截行为；
- 日志不包含临时目录字面量（文案约束），仅含守卫名、task_id、action。

### 5.3 fail-closed 说明（两层语义，避免误读）

| 层 | 机制 | 行为 |
|---|---|---|
| 审批门层（平台） | 守卫返回 approve → 进入人类审批门；审批被拒/超时/审批门自身异常 | **fail-closed（block）**：工具不执行（平台机制，需求 1.5 节，本插件不改动） |
| 插件判定层（本设计） | 守卫内部异常 → 项级捕获 → 该项按未命中 → 继续轮询 | **单守卫失效、其余继续**：这是需求 FR-14 明确定义的契约（非 fail-open）——C 项结构性排在最前，永不被 A/B 异常旁路（AC-10 组合①）；异常有 `logger.exception` 记录，可发现、可修复；A/B 之间互不影响（NFR-01） |

**关键区分**：真正的 fail-open 是「不实现项级隔离、依赖平台兜底导致整个插件放行」——本设计通过 5.1 模式杜绝；单守卫异常按未命中放行是该次调用层面的契约行为（需求接受，AC-10 验收），二者不可混为一谈。调度器外层 try/except（1.2）为防御性最后防线（DR-15）：正常情况不可达（项级隔离已兜住），其语义同为「异常=未命中=记录日志」，避免插件崩溃并保证可观测。

## 9. 风险与取舍（Alternatives / Trade-offs / Risks）

### 9.1 设计决策备选方案（Alternatives）

| 编号 | 议题 | 备选方案 | 取舍结论 |
|---|---|---|---|
| AL-1 | 受保护文件集合判定 | A：实时扫描 HERMES_HOME 目录树枚举 config 文件（精确但引入 IO，违反 NFR-05）<br>B：**前缀 + 文件名规则纯内存判定（采用，DR-06）** | 采用 B：零 IO、目录迁移即时生效；代价是「文件名含 config 即受保护」为近似规则（误拦方向，可接受，见 R4） |
| AL-2 | A 项 rule_key 粒度 | A：固定 key（如 `write_guard:config`）——字面更贴近需求 Q-04「该项」表述，但误选 always 后**整个配置写保护失效**（fail-open 方向）<br>B：**按归一化目标路径细粒度（采用，DR-12）** | 采用 B：失效面最小（单文件）；A 的语义差异已在 DR-12 说明为设计自由度内的选择 |
| AL-3 | A 项识别工具集 | A：对所有工具 args 全字符串兜底扫描<br>B：**仅四工具精确识别（采用，DR-08）** | 采用 B：Q-03 低误拦优先；A 会大量误拦（读工具路径、无关字符串都含受保护路径） |

| AL-5 | HERMES_HOME 读取时机 | A：模块加载时缓存一次<br>B：**每次调用实时读取（采用，DR-05）** | 采用 B：目录迁移即时生效、测试可控（TC-A-40~42）；性能成本可忽略（一次环境变量读 + 归一化，NFR-05） |

|---|---|---|---|

## 10. 部署与生效步骤（OOS-06：机制维持现状）

现有部署机制不变（deploy.py + 重启生效，插件代码改动不热加载）。扩展落地步骤（由主 Agent 按授权执行，本文档只给步骤）：

1. **实现**：按本设计修改 `handler.py`（分区结构见 1.1）、扩展 `test_handler.py`（用例见 7.2）；
2. **测试**：运行 `python test_handler.py`——现有 C 项用例 + 新增 A/B/调度/异常/消息用例全部通过，退出码 0、输出 ALL PASS（AC-01 / NFR-04）；
3. **部署**：运行 `python deploy.py` 将插件目录同步到部署目录（当前为 `D:\myagent\.hermes\plugins\write-guard\`，以 deploy.py 实际配置为准）；
4. **重启**：重启 Hermes Gateway（插件代码改动不热加载，重启后生效）；
5. **验证**（AC-02~07 实测项）：Gateway 启动日志无异常；实测 A 项（write_file/patch/terminal/execute_code 写受保护配置 → 触发审批）、B 项（写记忆工具 → 触发审批；查询工具 → 放行）、C 项回归（临时目录拦截行为与扩展前一致）；审批拒绝/超时 → 工具被阻止（fail-closed）；
6. 部署前确认插件已启用（`plugins.enabled` 含 write-guard）。

注：重启 Gateway、部署写盘均属变更操作，须先报告用户并获得授权后执行（workspace 纪律）；本设计不包含自动执行部署。

| DR-23 | 环境变量展开语义显式定义：变量名完整词边界正则（`[A-Za-z_][A-Za-z0-9_]*`），查找统一**大小写不敏感**（Windows 原生；POSIX 用键小写化比对辅助函数），不依赖 os.path.expandvars | MED-3、FR-04③ | os.path.expandvars 对 `$VAR` 大小写敏感，`$HERMES_home` 变体不展开即可绕过；统一内核 + TC-A-44/47 守门 |
| DR-24 | 等价类变体命中时审批消息双段展示「用户输入原文（对应文件：<归一化解析后绝对路径>）」；字面命中仍只展示原文（DR-16） | LOW-2、FR-06 | 变体命中只展示原文（相对路径 / 环境变量引用 / cd 链）时用户无法判断实际写入文件，FR-06「完整路径」字面未满足（TC-M-08） |
| DR-25 | 复制至受保护目录形态（`cp 源 目录\`、`-t` 目标为目录）：本期不识别、放行，显式声明为已知静态识别边界（OOS-03）；可选增强方案（按源文件名落盘判定）仅记录不实现 | LOW-5、OOS-03 | 落盘文件名依赖命令执行语义，静态不可靠识别；声明边界避免实现期误猜（TC-A-46） |
| DR-26 | `_judge_path_param` 首行防御：path 非字符串 / 空串 / 仅空白 → 直接返回 None（放行） | LOW-3、Q-03 | 无路径可判定即无命中标的；避免 None 传入归一化抛异常产生误导日志（不依赖项级异常兜底；TC-A-05） |
| DR-27 | 相对路径解析基准声明为设计假设：write_file / patch / execute_code = 进程当前工作目录（终端 cwd）；实现期必须对照 Hermes 源码核实并写注释，未核实时维持假设 + Q-03 兜底 | LOW-1、FR-04④ | Hermes 实际基准（workspace、会话目录等）未经源码核实；假设明确化避免实现期凭空猜测（未决项④跟踪） |
